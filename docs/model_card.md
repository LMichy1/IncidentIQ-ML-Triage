# Model card — `incident_category_classifier` v0.1.0

## What this model does

Given an incident's title and description, predicts one of 8 categories
(see taxonomy below). It does **not** predict priority or severity — see
[`priority_policy.md`](priority_policy.md) for why that's a separate,
non-learned, rule-based policy.

## Intended use

Demonstrating a complete, leakage-controlled ML pipeline (data → split →
baseline comparison → evaluation → versioned artifact) inside a working
triage application. **Not intended, and not validated, for production
incident triage decisions.**

## Training data

Synthetic, templated, seeded (`RANDOM_SEED=42`), 3,150 rows, every row
tagged `is_synthetic: true`. Full provenance and the audit of three
real-dataset candidates that were investigated and rejected (license gaps,
unverifiable schema, blocked downloads) is in
[`dataset_decision.md`](dataset_decision.md) — that document is the source
of truth; this card summarizes it, not the other way around.

**This is the single most important caveat on this card**: no metric below
says anything about how this model would perform on real incident reports.
It demonstrates that the pipeline is implemented correctly.

## Target taxonomy

`authentication_access`, `database_data_integrity`, `api_backend_error`,
`ui_frontend`, `performance_latency`, `infrastructure_deployment`,
`third_party_integration`, `security_vulnerability`. Full descriptions in
`dataset_decision.md`.

## Evaluation

| Model | Validation macro F1 |
|---|---|
| DummyClassifier (stratified) | ~0.14 |
| TF-IDF + Multinomial Naive Bayes | ~0.82 |
| **TF-IDF + Logistic Regression (selected)** | **~0.90** |

Test macro F1 (scored once, after selection): **~0.89**. Per-class
precision/recall/support and the confusion matrix are in the exported
artifact's `metadata.json` (`ml/artifacts/incident_category_classifier/0.1.0/`),
regenerated by `ml/scripts/train.py`.

**Development-stage result, not an independent estimate.** The dataset
generator was redesigned after an earlier version scored a meaningless 1.0
macro F1 on both validation *and* test — that observation informed the
`CONFUSABLE_PAIRS` redesign. Model selection was still validation-only, but
the dataset design itself was informed by a prior test score. See
["Evaluation-independence caveat"](dataset_decision.md#evaluation-independence-caveat-development-stage-result)
in `dataset_decision.md` for the full explanation. Do not quote the ~0.89
figure as a clean frozen-holdout number.

## Uncertainty and confidence

**No probability calibration has been performed.** The backend
(`backend/app/ml_runtime.py`) exposes the model's raw top-class probability
and the margin to the second-ranked class, but always labels them
`confidence_status: "uncalibrated"` — both the API and the frontend UI
carry this label through to the end user. These numbers must never be
presented or interpreted as "% confidence."

Human-review gating uses a fixed heuristic margin threshold
(`LOW_MARGIN_REVIEW_THRESHOLD = 0.20`, `backend/app/config.py`): a
prediction is flagged for human review when the gap between the top two
class probabilities is below that threshold. **This threshold is a
conservative placeholder, not a statistically validated cutoff** — it was
chosen by inspection, not fit against a labeled calibration set. Revisiting
it requires real or higher-fidelity data with known ground truth, which
this project does not have.

## Limitations

- Synthetic training data (see above) — no real-world performance claim.
- No calibration — raw scores only, explicitly labeled as such.
- Heuristic (not validated) human-review threshold.
- Fixed 8-category taxonomy; inputs describing something outside it are
  forced into the nearest class rather than flagged as out-of-scope.
- Priority/severity is out of scope for this model by design — see
  `priority_policy.md`.
- A human-review feedback mechanism exists (M3 — see
  `docs/architecture.md#feedback-data-model-m3`) and records reviewer
  corrections, but nothing consumes them: there is no retraining loop,
  drift monitoring, or reviewer-agreement metric built on top of it yet.

## Versioning

`model_name`/`model_version`/`algorithm`/`class_labels`/`artifact_sha256`
are all recorded in `metadata.json` alongside the artifact, and the backend
refuses to load an artifact whose file hash doesn't match what's recorded
there (see `backend/app/ml_runtime.py`).
