# Dataset decision

**Decision date:** 2026-09-22
**Decision:** Use a clearly labeled **synthetic demonstration dataset**, not a
real-world bug/incident corpus, for the Milestone 1 baseline.

This is not a default — it is the documented fallback the project brief
itself authorizes when no candidate clears the provenance/license bar. Three
real candidates were investigated and rejected; the audit trail is below so
the decision can be revisited once there's time to pursue a real dataset (see
"Future work").

## Candidates evaluated

### 1. `ansymo/msr2013-bug_dataset` (Eclipse/Mozilla, Lamkanfi et al., MSR'13) — rejected

- **Source:** https://github.com/ansymo/msr2013-bug_dataset — confirmed reachable,
  plain-HTTPS tarballs (`data/eclipse.tar.gz`, 9.2MB; `data/mozilla.tar.gz`, 35.8MB),
  no auth required. Downloaded and inspected directly.
- **Provenance:** Mined from Eclipse and Mozilla Bugzilla (~2006-era data per
  timestamps) for the cited MSR'13 paper. Solid academic provenance.
- **Fields confirmed present:** `short_desc` (title), `severity` (with full
  history), `priority` (with full history), `product`, `component`,
  `bug_status`, `resolution`, `assigned_to`, `cc`, `op_sys`, `version`,
  `opening_time` (Unix timestamp), `reporter`.
- **Rejection reason 1 — no description field.** There is no `long_desc` /
  free-text description anywhere in this dataset, only the one-line
  `short_desc`. Our brief requires title **and** description as input; this
  dataset only supports title-only classification.
- **Rejection reason 2 — license.** GitHub's license API reports
  `license: None`; there is no `LICENSE` file and the README states no
  explicit reuse terms. Provenance is real, but there is no formal grant of
  reuse rights we can point to beyond "cite the paper." This does not clear a
  verifiable-license bar.
- **Useful confirmation regardless:** `severity` and `priority` are tracked as
  separate, independent fields with their own histories — this directly
  confirms the literature pattern behind [`priority_policy.md`](priority_policy.md):
  `priority` in Bugzilla-derived data is reporter-set and not a reliable
  proxy for real incident severity, whereas `severity` is the more meaningful
  (if still noisy) triage label. We are still not using either as a
  supervised priority target — see that document for why.
- No `duplicate_of` field present in this particular export (it exists in
  live Bugzilla / raw dumps but wasn't carried into this dataset).

### 2. PROMISE / Zenodo "BugRepo" (10.5281/zenodo.1246025) — rejected for now

- **License:** confirmed **CC BY 4.0** via the Zenodo API — this is the one
  candidate with an unambiguous, verifiable license.
- **Rejection reason:** archives are 722MB and 2.8GB. Per the brief's explicit
  caution against downloading enormous archives without first assessing a
  smaller legitimate subset, and given we could not inspect the internal
  schema before committing to the download, we did not pull this for the M1
  deadline. This is the strongest candidate for a future real-data pass (see
  below) — the license problem is solved, only the size/schema-verification
  work remains.

### 3. `av9ash/gitbugs` Mozilla Core dataset — rejected

- Small in-repo CSV (330KB) contains only `issue_id`/`duplicate_id` pairs — no
  title, description, or label fields.
- The full dataset (65MB, claimed to have real fields) is hosted on Google
  Drive behind an interactive virus-scan click-through page; a scripted HTTPS
  fetch fails. Not usable in a sandboxed/reproducible pipeline.
- The repo's README is a generic template reused across unrelated datasets
  (it references "Hadoop version" for a non-Hadoop dataset), so its claimed
  schema/license (CC BY 4.0) could not be independently trusted without
  fetching the actual file, which we could not do.

## Why not just use the Eclipse data title-only

We considered relaxing to title-only classification on the Eclipse subset
purely to get a real dataset, but the license gap is the harder blocker of
the two — "cite the paper" is not a redistribution/reuse grant, and we are
not comfortable shipping a "real-world dataset" claim we can't back with a
license. The missing description field would also mean silently narrowing
scope without flagging it, which the brief also warns against. Synthetic-but-
honest beats real-but-unlicensed for this deadline.

## The synthetic dataset

Generated by [`ml/scripts/generate_dataset.py`](../ml/scripts/generate_dataset.py),
seeded (`RANDOM_SEED=42`) for reproducibility. Every row carries
`is_synthetic: true`. See that script and `ml/src/incidentiq_ml/config.py` for
the exact category taxonomy, template vocabulary, and generation parameters.

**What it is:** ~3,000 templated `(title, description)` pairs across 8
incident categories, with realistic class imbalance, injected near-duplicate
clusters (to exercise the duplicate-audit step), a `reporter_id` for
group-aware splitting, and `created_at` timestamps spread over 18 months for
temporal splitting.

**What it is explicitly not:** a source of real-world predictive-performance
claims. Any metric reported against it demonstrates that the pipeline
(preprocessing → split → train → evaluate → artifact) works correctly and
without leakage — it says nothing about how the model would perform on real
incident reports. This is stated again in the model card.

**Target taxonomy (category classification):**

| Category | Description |
|---|---|
| `authentication_access` | Login, SSO, permissions, session/token failures |
| `database_data_integrity` | Query failures, corruption, migration issues, data loss |
| `api_backend_error` | 5xx errors, unhandled exceptions, backend service failures |
| `ui_frontend` | Rendering bugs, broken layouts, client-side JS errors |
| `performance_latency` | Slow responses, timeouts, resource exhaustion |
| `infrastructure_deployment` | Deploy failures, container/orchestration issues, config drift |
| `third_party_integration` | Failures in external API/webhook/payment-provider integrations |
| `security_vulnerability` | Reported vulnerabilities, injection, exposure, CVE-driven reports |

No `priority` field is generated at all — deliberately, to avoid reproducing
the exact mistake (treating ticket priority as ground-truth severity) the
brief warns against. See [`priority_policy.md`](priority_policy.md).

**Deliberate category confusability.** The first version of the generator
gave every category fully disjoint vocabulary, which produced a meaningless
1.0 macro F1 for every real model on the very first training run — that's a
sign the benchmark is too easy to say anything, not a result worth reporting.
The generator now borrows subject/symptom vocabulary from a paired,
plausibly-confusable category for ~18% of rows (e.g. `api_backend_error` /
`third_party_integration`, `authentication_access` / `security_vulnerability`)
so the classification task has genuine ambiguity, closer to how real triage
disagreements happen. See `CONFUSABLE_PAIRS` in
[`generate_dataset.py`](../ml/scripts/generate_dataset.py).

## Duplicate audit finding

[`ml/src/incidentiq_ml/data/dedup_audit.py`](../ml/src/incidentiq_ml/data/dedup_audit.py)
detects duplicates the way we'd have to on real data — exact text match plus
TF-IDF cosine similarity — without relying on the synthetic `dup_group_id`
oracle field. Run against the actual generated dataset:

| Threshold | Pairs flagged | True positives (match `dup_group_id`) | Precision |
|---|---|---|---|
| 0.85 | 5,129 | 135 | 3% |
| 0.90 | 1,046 | 128 | 12% |
| 0.95 | 131 | 128 | 98% |
| 0.97 | 101 | 101 | 100% |

At 0.85 the detector is nearly useless here — the heavily templated
generation means unrelated same-category reports already look very similar,
so a loose threshold mostly flags coincidental template overlap, not real
duplicates. 0.95 is the threshold actually used by default (~85% recall of
the 150 injected near-duplicates at ~98% precision). This is reported as a
finding, not hidden: it's a genuine threshold-tuning tradeoff, and a real
corpus would need its own calibration against a labeled duplicate sample
rather than reusing this number.

## Future work (explicitly deferred, not part of M1)

Revisit the Zenodo PROMISE `BugRepo` (CC BY 4.0, verifiable license) as a real
follow-up dataset: pull a bounded subset (not the full 2.8GB archive),
inspect its schema for a genuine title+description pair and a duplicate/near-
duplicate signal, and only then consider retraining on real data. Also worth
checking: Eclipse's and Mozilla's live Bugzilla REST APIs are public,
HTTPS, no-auth, and do return `summary` + comment text + `severity` +
`dupe_of` + timestamps per bug — a small, rate-limited pull against those
(with the actual Bugzilla terms of use reviewed first) is a plausible path to
a small, real, well-licensed dataset without downloading a multi-GB archive.
